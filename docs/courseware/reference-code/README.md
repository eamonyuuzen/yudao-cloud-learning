# Reference Code 使用规则

这里保存提前备好的完整关键实现，目的是避免正式学习时临时生成答案，不是让用户跳过思考。

## 状态标签

- `READY-DESIGN`：文件、方法、SQL 和测试形状已准备；集成前要重新对照当前分支。
- `SOURCE-VERIFIED`：已经用当前源码/窄测试验证某个机制，但不是完整业务集成。
- `RUNNABLE-LAB`：独立 Lab 已运行自动测试。
- `INTEGRATED`：已经进入 Yudao 业务源码并通过编译/测试。

当前 Java 参考卡均为 `READY-DESIGN`，因为第 7～10 步会依次改变同一业务，提前全部写入主源码会破坏学习节奏并制造未验证耦合。

例外：[Step 06B Java Tool 注册闭环](step06b-java-tool-registration.md) 已通过不调用
模型的窄测试，状态为 `SOURCE-VERIFIED`。

[Step 06B Pi Agent Core 源码迁移卡](step06b-pi-agent-loop.md) 是
`SOURCE-READING`：它只用来将手写 Agent loop 迁移到真实运行时源码，
不引入依赖，也不替换现有 Python Lab。

[Step 06B Agent 开源仓库取样卡](step06b-agent-repository-sampling.md) 记录
不同仓库的当前用途和停止边界；它是选材索引，不是新增的学习主线。

## 开始某阶段时

1. 确认当前分支和工作区；
2. 对照参考卡中的“基线假设”；
3. 用户先完成不变量和伪代码；
4. 再选择复制、改写或由 AI 应用参考实现；
5. 运行卡片中的最小编译和测试；
6. 将状态更新为 `INTEGRATED` 只能基于真实证据。

## 不可直接复制的内容

- 错误码编号：若主分支已占用，必须重新选择；
- 数据库 migration 名和版本：按执行时规则确定；
- 线程池容量：必须结合当时机器和下游容量；
- Redis TTL/限流次数：先作为实验参数，再由数据校准；
- MQ 重试次数：必须与业务恢复方式一起决定。

当前基线中的预留顺序仅用于避免四张参考卡彼此撞号：

| 编号后缀 | 参考语义 |
|---:|---|
| 000～001 | 已有：任务不存在、状态流转非法 |
| 002～003 | Step 07：已认领、不可认领 |
| 004 | Step 08：Job 不存在/不可见 |
| 005～006 | Step 09：任务繁忙、Job 请求重复 |
| 007 | Step 10：并发下状态已变化 |

真正集成前仍要在 `ErrorCodeConstants` 全文件重新搜索。

## 安全

所有示例只使用占位配置；不得把真实 Token、密码、API Key 或连接串补进本目录。
