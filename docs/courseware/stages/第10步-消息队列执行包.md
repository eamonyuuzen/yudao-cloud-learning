## 0. 先回答为什么需要 MQ

同步耦合：

```text
更新任务状态
→ 写审计
→ 发邮件
→ 发站内信
→ 更新统计
→ 全部完成后才返回
```

问题：

- 一个非核心通知失败可能拖垮主业务；
- 请求时间随下游增加；
- 生产者知道太多消费者；
- 瞬时洪峰直接压到下游。

事件驱动：

```text
任务状态事务成功
→ 发布 TaskStatusChangedEvent
→ 主请求结束

各消费者按自己的速度：
→ 审计消费者
```

现实比喻：

> 学校广播站播报“课程取消”。教务、老师和学生各自处理，不需要广播员逐个打电话并等待所有人确认后才算播报。

比喻边界：可靠 MQ 不是喊一嗓子就结束。消息需要保存、确认、重试和失败恢复；消费者仍可能重复听到。

还要补上“部门”边界：

```text
不同业务部门 = 不同 consumer group
→ 审计组、通知组各自都能处理同一事件

同一部门的多个 worker = 同一 group 内竞争
→ 一条消息只分给其中一个 worker
```

同一 consumer group 不是广播给每个 consumer。

当前 Yudao 默认把 `AbstractRedisStreamMessageListener.group` 设为
`spring.application.name`。因此同一应用里直接复制“审计 Listener + 通知
Listener”，两者会进入同组竞争，不能保证都收到。核心版只实现审计 Listener；
扩展通知前必须先设计并验证显式 group（或拆 stream/应用）。

## 1. 第 1 日：消息模型与边界

### 根问题

> 哪些动作适合从主事务拆出去，哪些必须留在主事务？

必须同步：

```text
任务状态合法性
认领人
关键业务记录
```

可以异步：

```text
邮件/站内信
非关键统计
搜索索引刷新
外部系统通知
```

### Event 与 Command

```text
Event：
“任务 10 已完成”
→ 描述已经发生的事实

Command：
“请给用户 2 发送提醒”
→ 要求某个处理者执行动作
```

第一版事件：

```json
{
  "eventId": "唯一 ID",
  "taskId": 10,
  "oldStatus": 1,
  "newStatus": 2,
  "operatorUserId": 2,
  "occurredAt": "时间"
}
```

消息只放完成消费所需的稳定字段，不把完整 DO、Token 或敏感用户资料塞进去。

### 用户决策

1. `eventId` 谁生成？
2. 消费者根据什么去重？
3. 任务标题放消息里还是消费时查库？
4. 消息版本以后怎样演进？

## 2. 第 2 日：读 Yudao Redis Stream 运行闭环

### 核心文件

第一入口：

1. [AbstractRedisStreamMessageListener.java](../../../yudao-framework/yudao-spring-boot-starter-mq/src/main/java/cn/iocoder/yudao/framework/mq/redis/core/stream/AbstractRedisStreamMessageListener.java)

再按问题最多打开：

2. [AbstractRedisStreamMessage.java](../../../yudao-framework/yudao-spring-boot-starter-mq/src/main/java/cn/iocoder/yudao/framework/mq/redis/core/stream/AbstractRedisStreamMessage.java)
3. [RedisMQTemplate.java](../../../yudao-framework/yudao-spring-boot-starter-mq/src/main/java/cn/iocoder/yudao/framework/mq/redis/core/RedisMQTemplate.java)
4. [YudaoRedisMQConsumerAutoConfiguration.java](../../../yudao-framework/yudao-spring-boot-starter-mq/src/main/java/cn/iocoder/yudao/framework/mq/redis/config/YudaoRedisMQConsumerAutoConfiguration.java)
5. [RedisPendingMessageResendJob.java](../../../yudao-framework/yudao-spring-boot-starter-mq/src/main/java/cn/iocoder/yudao/framework/mq/redis/core/job/RedisPendingMessageResendJob.java)

### 启动闭环

```text
Spring 扫描到具体 MessageListener Bean
→ AutoConfiguration 收集所有 Listener
→ 为每个 stream/group 建消费者组和监听容器
→ worker 开始轮询/接收消息
```

### 运行闭环

```text
Producer 构造 Message
→ RedisMQTemplate XADD 到 stream
→ Consumer Group 中某消费者读到
→ 框架反序列化为具体消息
→ 调用 onMessage
→ 成功后 ACK
→ 失败时不 ACK
→ 在消息体仍存在的前提下进入 pending，并由当前任务尝试重投
```

必须用当前源码确认 ACK 和异常行为，不能把 RabbitMQ/Kafka 规则直接套过来。
高积压时 Stream 裁剪可能先删除 pending 对应消息体，因此不能概括成“进入
pending 就必然恢复”；核心实验只证明正常规模下的一次重投。
租户上下文不是靠旧 Token 长期传递；Yudao 的
`TenantRedisMessageInterceptor` 会把 tenantId 放入消息 Header，并在消费侧
恢复。它正好复用此前“HTTP Header 是运输载体”的认知，但载体换成了 MQ Header。

### 深度边界

需要理解：

- stream、consumer group、consumer、pending；
- ACK 是消费者确认处理结果；
- 至少一次语义为什么导致重复；
- 消费者停机后消息为何仍在；
- 清理和 pending 重投的大致边界。

暂不追 Redis Stream 内部 radix tree、RDB/AOF 实现。

## 3. 第 3 日：实现 Producer 与 Consumer

### 文件地图

```text
InternshipTaskStatusChangedMessage
→ 定义事件数据和 stream key

InternshipTaskStatusChangedProducer
→ 构造并发送消息

InternshipTaskStatusChangedConsumer
→ 收到消息、幂等检查、调用业务

InternshipTaskEventAuditDO/Mapper
→ 第一版同时充当审计副作用与 eventId 唯一底线
```

### 为什么 Producer 不写在 Controller

Controller 只负责 HTTP。真正知道“状态变化已经成功”的是 Service 事务。事件的业务含义也属于 Service。

### 第一版调用点

```text
claim Service：
TODO→IN_PROGRESS + assignee + claim
→ 事务成功后发布认领事件

update-status Service：
只允许 IN_PROGRESS→DONE
→ 事务成功后发布完成事件
```

不能保留一个普通 `update-status` 的 `TODO→IN_PROGRESS` 入口：它会绕过第 7 步
建立的 `assignee + claim` 不变量。事件接入时应复用既有业务入口，而不是为同一
状态变化再造第二条路。

直接在事务方法中 `send` 存在一致性窗口：

```text
数据库提交成功，但发消息失败
数据库回滚，但消息已经发出
```

第 10 步先明确观察这个缺口；可靠 Outbox 在第 14 步系统解决。当前可选用 Spring 事务提交后回调降低“回滚却发出”的风险，但“提交后发送失败”仍需补偿。

### 用户亲手完成

- 消息字段；
- 事件在哪个业务时刻产生；
- 消费幂等键；
- 消费失败是否重试；
- 哪些错误属于永久错误。

AI 补序列化、Bean、普通 Mapper 和日志。

## 4. 第 4 日：重复消费与幂等

### 根问题

> 消息已经成功处理，为什么还可能再次投递？

典型时间线：

```text
消费者完成业务写入
→ 进程在 ACK 前宕机
→ MQ 不知道业务已经完成
→ 消息再次投递
```

因此不能依赖“MQ 只发一次”。

### 消费幂等方案

第一版使用数据库唯一键：

```sql
UNIQUE KEY uk_event_consumer (event_id, consumer_name)
```

人类逻辑：

```text
开始消费
→ 尝试插入处理记录/检查唯一键
→ 已存在：直接视为已处理
→ 不存在：执行业务并完成记录
```

第一版只选择一个可证明的小副作用：写数据库审计。审计行本身携带
`eventId + consumerName` 唯一键，并在同一事务完成。

外部邮件不是数据库事务能天然保护的副作用；以后需要供应商幂等键、发送状态
或 Outbox，不能直接套用“插消费记录就一定安全”。

Redis 去重只能做快速层，TTL 过期后仍可能重复；数据库唯一约束保存最终底线。

### 实验

同一个 `eventId` 人工发送 10 次：

```text
Consumer onMessage 调用次数可以大于 1
真正业务副作用只能是 1
处理记录只能是 1
```

## 5. 第 5 日：当前 pending 重投与永久失败缺口

### 错误分类

可重试：

- 临时网络故障；
- 下游 5xx；
- 数据库短时不可用；
- 锁等待/死锁（有上限）。

不可直接重试：

- 消息字段缺失；
- 状态值非法；
- 业务对象永久不存在；
- 权限/配置永久错误；
- 代码 bug。

### 当前核心事实

```text
Consumer 抛异常
→ Listener 不 ACK
→ 消息进入 pending
→ 当前重投 Job 扫描并尝试重写
```

当前通用框架没有业务级最大重试次数与 DEAD 表。因此核心实验不能要求观察
不存在的“达到上限”。无限失败仍可能形成毒消息，需要留下告警与治理缺口。

### OPTIONAL：有限重试与失败记录

至少保存：

```text
eventId
consumerName
retryCount
lastErrorCode
lastErrorMessage
nextRetryTime
status
```

不保存完整 Token、Prompt 或敏感正文。

### 实验

让消费者对某个特定 `taskId` 固定失败：

```text
观察进入 pending
→ 等待一次重投
→ 证明异常没有被 ACK
```

只有实现了独立失败表和最大次数后，才追加：

```text
达到上限 → DEAD/FAILED → 修复后人工重放
```

## 6. 第 6 日（OPTIONAL）：积压、顺序和削峰

### 根问题

> Producer 每秒 1000 条、Consumer 每秒 100 条时，消息去了哪里？

积压增长：

```text
每秒净增加 900 条
```

必须观察：

```text
stream 长度
pending 数
最老消息等待时间
消费速率
失败率
消费者数量
```

### 扩容不是无限的

增加 Consumer 会受到：

- Redis/网络能力；
- 数据库连接池；
- 下游限流；
- 同一任务的顺序约束；
- 消费业务锁竞争。

### 顺序

如果同一 taskId 连续产生：

```text
TODO→IN_PROGRESS
IN_PROGRESS→DONE
```

并行消费者可能乱序处理。第一版审计消费者可以按事件发生时间记录并检查状态；需要强顺序时按业务 Key 分区/串行，不能假设全局队列天然满足所有业务顺序。

Redis Stream 的具体消费顺序需要按当前 consumer group 行为验证。

### 削峰

MQ 把瞬时请求变成可排队工作，但没有消灭总工作量：

```text
峰值变平
→ 用户等待变长
→ 必须有积压指标和容量计划
```

## 7. 第 7 日：与 Agent 和前面步骤组合

### Agent 工具

可开放：

```text
query_task_status(taskId)
query_job_status(jobId)
```

受控写工具候选：

```text
start_report_job(requestId, filters)
```

写工具必须经过：

```text
用户确认
→ 权限
→ 参数上限
→ 幂等 requestId
→ 创建 job
→ 返回 jobId
```

Agent 不等待 MQ 消费全部完成，而是：

```text
提交
→ 告知 jobId
→ 后续查询状态
```

### 6B～10 总链

```text
报告 Job 支路：
自然语言 → 受控工具 → 权限/限流/幂等
→ MySQL 登记 job → JVM 线程池执行 → MySQL 保存 job 状态

状态事件支路：
任务状态事务成功 → Redis Stream
→ 当前 system-server 默认 consumer group
→ 第一版审计消费者处理并 ACK

通知扩展支路：
先补显式 consumer group 能力并验证广播边界
→ 再加入通知消费者

Agent 后续查询：
读取 MySQL 中的任务/job 事实 → 回答用户
```

线程池与 MQ 都能异步，但不是一个模糊可互换盒子：前者是当前进程内执行器，
后者是跨进程可恢复的消息载体。什么时候让 MQ 替代内存队列，是阶段末决策题。

### 回归矩阵

| 场景 | 预期 |
|---|---|
| 正常事件 | producer→stream→consumer→ACK |
| 消费者暂时停机 | 消息保留，恢复后消费 |
| Consumer 业务异常 | pending 与一次重投可观察 |
| 同 eventId 10 次 | 业务副作用 1 次 |
| 永久非法消息 | 核心版明确缺少上限；扩展版才人工处理 |
| 大量消息 | 能看到积压和消费速率 |
| 主事务回滚 | 不应生成“已经成功”的有效事件 |
| 数据库提交后发送失败 | 明确当前缺口；不冒充已实现补偿 |

### 进入第 11 步或综合作品的门槛

- 能区分事件与命令；
- 能画出 Producer、Broker、Consumer、ACK 的时间线；
- 真实观察过重复消费和消费失败；
- 消费者有数据库幂等底线；
- 能解释 MQ 解决解耦/削峰/异步，但不自动保证业务一致；
- 知道 Outbox 为什么要等可靠性阶段系统学习。
