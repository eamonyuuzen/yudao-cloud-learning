## 0. 先建立业务模型

### 能力

```text
用户认领一个待处理任务
→ 该任务记录认领人
→ 状态变为进行中
→ 新增一条认领记录
```

### 核心不变量

```text
一个任务最多一个认领人
只有 TODO 可以被认领
认领人和 IN_PROGRESS 必须同时出现
任务更新和认领记录必须一起成功或一起失败
```

### 为什么选择它

它不是为了给实习任务增加大量产品功能，而是用一个最小业务回答两个基础问题：

1. 多条数据库语句怎样成为“一个业务动作”？
2. 两个请求同时执行同一个业务动作时，怎样保证只有一个成功？

### 现实比喻

事务像银行柜台办理转账：

```text
从 A 账户扣钱
→ 给 B 账户加钱
```

柜员写完第一张单据后电脑故障，不能让钱只扣不加。事务保护的是“整件业务”，不是让每条 SQL 永远不失败。

并发认领像两个人同时拿同一把储物柜钥匙。只在 Java 里“先看桌上有没有钥匙，再去拿”会发生两个人都看见钥匙；真正的裁决必须在共享事实所在的位置完成——这里是数据库。

比喻边界：数据库锁不是把整栋楼锁住；锁的范围取决于 SQL、索引、隔离级别和访问顺序。

## 1. 第 1 日：一条业务为什么需要事务

### 根问题

> `@Transactional` 保护的是哪些动作，什么时候才算提交？

### 人类逻辑

```text
进入认领方法
→ 开始一个事务
→ 原子更新任务
→ 插入认领记录
→ 方法正常结束
→ 提交事务

任一步抛出符合回滚规则的异常
→ 回滚本事务内已经执行的 SQL
```

### 先看现有代表代码

只读：

1. [WmsInventoryServiceImpl.java](../../../yudao-module-wms/yudao-module-wms-server/src/main/java/cn/iocoder/yudao/module/wms/service/inventory/WmsInventoryServiceImpl.java)
   中一个带 `@Transactional` 的完整方法；
2. [AdminUserServiceImpl.java](../../../yudao-module-system/yudao-module-system-server/src/main/java/cn/iocoder/yudao/module/system/service/user/AdminUserServiceImpl.java)
   中一个“主表 + 关联表”的事务；
3. 当前 [InternshipTaskServiceImpl.java](../../../yudao-module-system/yudao-module-system-server/src/main/java/cn/iocoder/yudao/module/system/service/internship/InternshipTaskServiceImpl.java)。

只比较：

| 问题 | 证据 |
|---|---|
| 事务从哪个方法进入？ | 注解所在 public 方法 |
| 哪些 Mapper 调用属于同一事务？ | 同一线程、同一数据源、同一事务上下文 |
| 什么时候提交？ | 代理看到方法正常返回 |
| 什么时候回滚？ | 代理捕获符合规则的异常 |

### 框架机制到哪一层

需要理解：

```text
启动：
Spring 发现事务管理器和 @Transactional 规则
→ 给符合条件的 Bean 建立事务 Advisor/代理

运行：
外部调用代理方法
→ 代理开启/加入事务
→ 调原方法
→ 正常则提交，异常则按规则回滚
```

暂不追 `TransactionInterceptor` 全部源码。

### 验收

能说明为什么把注解写在 DO、Mapper 或普通私有辅助方法上通常不能自动形成预期事务边界。

## 3. 第 3 日：事务为什么会失效

### 根问题

> 明明写了 `@Transactional`，为什么数据库仍可能不回滚？

只做四个最有价值的对照：

1. `public` 代理方法由外部 Bean 调用；
2. 同类内部 `this.transactionalMethod()`；
3. 捕获异常后吞掉；
4. 抛出 checked exception 但未配置回滚规则。

### 动态事件对比

正确：

```text
Controller/另一个 Bean
→ Spring 代理
→ 开事务
→ 原 Service 方法
```

同类自调用：

```text
原 Service 方法
→ this.另一个方法
```

第二条没有重新经过代理，因此方法上的事务元数据没有新的运行时接收者。

### 用户任务

画出四种情况谁先接住调用，并预测是否回滚。只运行其中两个代表实验，不必把所有陷阱写进业务源码。

### 验收

不背“八大失效场景”，而是能用一个判断定位：

> 这次真实调用有没有先经过承载事务拦截器的 Spring 代理？异常最终有没有回到代理？

## 4. 第 4 日：制造并发错误

### 根问题

> 两个请求都在各自代码里判断 `status == TODO`，为什么仍可能都成功？

### 时间线

```text
任务初始：TODO，无认领人

请求 A：SELECT → 看见 TODO
请求 B：SELECT → 也看见 TODO
请求 A：UPDATE → 认领人 A
请求 B：UPDATE → 认领人 B
```

如果两个请求都插入认领记录，最终可能出现：

- 任务表认领人是 B；
- 认领记录同时有 A/B，或后插入失败；
- API 曾向 A 返回成功，但最终事实不属于 A。

### 用户编写并发测试的关键部分

```text
准备同一 taskId
→ 用 CountDownLatch 让两个线程尽量同时起跑
→ 每个线程使用独立事务调用认领
→ 等待结束
→ 统计成功/失败
→ 查询最终任务和认领记录
```

AI 可补 Executor、Future 收集和测试清理。

### 验收指标

```text
成功数必须是 1
失败数必须是 1
最终 assignee 与唯一认领记录一致
任务状态是 IN_PROGRESS
```

如果只断言“没有抛异常”，测试无效。

## 5. 第 5 日：比较四种并发方案

### 方案 A：`synchronized`

适合：

- 单 JVM；
- 同一对象实例；
- 进程不扩容。

局限：

- 多个服务实例各有自己的锁；
- 不能替代数据库约束；
- 事务提交时机可能晚于 Java 锁释放，需要检查边界。

### 方案 B：悲观锁 `SELECT ... FOR UPDATE`

人类逻辑：

```text
事务 A 锁住任务行
→ 读状态并更新
→ 提交释放
→ 事务 B 获得锁后看到新状态并失败
```

重点：

- 必须在事务内；
- 查询条件要命中索引；
- 锁等待、超时和死锁需要处理；
- 访问顺序不一致会放大死锁风险。

### 方案 C：乐观锁 `version`

```sql
UPDATE ...
SET assignee_user_id = ?, status = ?, version = version + 1
WHERE id = ? AND version = ?;
```

影响行数为 0 表示“读取后事实已经变化”，不是数据库宕机。

### 方案 D：条件原子更新

```sql
UPDATE system_internship_task
SET assignee_user_id = :userId, status = :inProgressStatus
WHERE id = :taskId
  AND status = :todoStatus
  AND assignee_user_id IS NULL;
```

这是带命名占位符的伪 SQL；真实 MyBatis 代码使用方法参数或 Wrapper，不把
`TODO` 当作数据库可识别的裸常量复制进去。

本业务第一版推荐 D：

- 竞争只发生一次；
- 不需要先读后写；
- SQL 直接表达不变量；
- 通过影响行数判断胜负。

若还需要一起写认领记录，在 Service 上用事务包住“原子更新 + 插入记录”。

### 用户决策

用户必须回答：

1. 本业务为什么不先上 Redis 分布式锁？
2. 条件原子更新的条件漏掉 `assignee_user_id IS NULL` 会怎样？
3. 更新影响 0 行时怎样区分任务不存在、状态错误和已被认领？

## 6. 第 6 日：隔离级别、MVCC 与锁只学到够用

### 根问题

> 为什么普通 `SELECT` 和 `SELECT ... FOR UPDATE` 看见的世界不同？

### 最小模型

```text
快照读：
普通 SELECT 主要根据 MVCC 读符合可见性规则的版本

当前读：
UPDATE / DELETE / SELECT ... FOR UPDATE
读取较新的可用记录并参与加锁
```

### 两事务小实验

终端 A：

```sql
START TRANSACTION;
SELECT status FROM system_internship_task WHERE id = ?;
```

终端 B 修改并提交。

终端 A 再普通查询和 `FOR UPDATE`，记录观察结果。先查询当前 MySQL 隔离级别，不把某一结果当成所有数据库通用规律。

### 深度边界

需要掌握：

- 读已提交与可重复读的主要差异；
- 快照读/当前读；
- 行锁依赖索引定位；
- 范围条件可能涉及间隙；
- 死锁由数据库检测并回滚一个事务。

暂不深入：

- undo log 物理格式；
- read view 源码；
- B+Tree 页锁细节；
- 所有隔离异常的学术变体。

## 7. 第 7 日：死锁与恢复

### 根问题

> 两个事务各拿一部分资源并等待对方时，系统怎样恢复？

### 最小实验

任务 1、任务 2：

```text
事务 A：先锁任务 1，再锁任务 2
事务 B：先锁任务 2，再锁任务 1
```

观察：

- 哪个事务被回滚；
- 应用收到什么异常；
- 数据库状态是否保持一致；
- 重试应放在哪一层；
- 为什么“永远重试”危险。

### 设计规则

优先：

```text
所有代码按相同顺序访问资源
→ 缩短事务时间
→ 减小锁范围
→ 让 SQL 命中索引
→ 对可重试死锁做有上限、带退避的重试
```

不把 `Thread.sleep` 放进持锁事务中模拟业务等待。

## 8. 第 8 日：完整接口和权限

### 入口

```text
PUT /admin-api/system/internship-task/claim?id=...
```

建议权限：

```text
internship:task:claim
```

不要复用 `update` 或 `update-status`，因为“认领”有独立业务语义、不变量和将来可能的数据权限。
引入认领后还要封住旧入口：普通 `update-status` 只保留
`IN_PROGRESS → DONE`；原“开始”动作改走 claim。否则同一个状态变化会有两条
道路，其中一条不会写 `assigneeUserId` 和认领记录。
同时把该字符串作为按钮权限资源补进
`sql/mysql/system_internship_task_menu.sql`。`@PreAuthorize` 只负责检查，
菜单 SQL 才让管理员能在角色配置页看见并授予它；插入权限资源本身不等于自动
给普通角色授权。

### 文件地图

```text
Controller：运输 taskId 和当前 userId
Service：事务、业务状态和失败语义
Task Mapper：原子条件更新
Claim Mapper：认领记录
DO/SQL：保存事实和唯一约束
Menu SQL：让 claim 成为可配置权限资源
Test：证明回滚与并发
```

### 错误语义

至少区分：

```text
TASK_NOT_EXISTS
TASK_NOT_CLAIMABLE
TASK_ALREADY_CLAIMED
```

是否完全区分可根据一次额外查询决定；不能把并发竞争失败统一伪装成服务器错误。

## 9. 第 9 日：阶段收口

### 回归矩阵

| 场景 | 预期 |
|---|---|
| TODO 首次认领 | 成功，状态/认领人/记录一致 |
| 同一用户重复认领 | 按契约返回已完成或明确重复 |
| 两用户并发认领 | 仅一个成功 |
| 非 TODO 认领 | 业务失败，无写入 |
| 普通 update-status 尝试 TODO→IN_PROGRESS | 被拒绝，必须走 claim |
| 更新后人工异常 | 任务和记录一起回滚 |
| 无权限 | Service 不执行 |
| 任务不存在 | 明确错误 |

### 用户最终复述

```text
事务解决“多步是否一起完成”
并发控制解决“多个执行者同时争用事实”
唯一约束保存数据库底线
原子 SQL 让数据库直接裁决不变量
锁是备选协调手段，不是所有并发问题的第一答案
```

### 进入第 8 步前的门槛

- 能画出事务代理的启动和运行闭环；
- 能人工制造并观察一次回滚；
- 能用时间线解释朴素先查再改为什么错；
- 能让并发测试稳定证明只有一个成功；
- 能说明为什么本场景选择原子 SQL。
