## 0. 先把“异步”说成人类逻辑

同步：

```text
HTTP 线程接到请求
→ 自己把所有工作做完
→ 才返回响应
```

异步：

```text
HTTP 线程登记一张工作单
→ 把工作放进有容量限制的队列
→ 立即返回 jobId

线程池中的工人稍后取走工作单
→ 执行
→ 把 SUCCESS / FAILED 写回数据库
```

现实比喻：

> 餐厅前台不亲自炒菜。前台登记订单并返回取餐号，厨房队列和厨师线程继续工作。队列满时必须停止接单或降级，不能假装订单已经成功。

比喻边界：线程池不是另一个服务器；它仍在同一个 Java 进程里，进程重启时内存队列中的任务可能丢失。

## 1. 本阶段业务状态机

```text
PENDING
→ RUNNING
→ SUCCESS
→ 或 FAILED
```

第一版暂不做重试、暂停和取消；`RETRYING` 等状态等恢复契约确定后再引入。

核心不变量：

- 提交接口成功，只代表数据库中已有工作单，不代表内存队列投递可靠，更不代表业务完成；
- 每个 job 必须能查询最终状态和失败原因；
- 后台异常不能只打印日志；
- 队列满时必须有可观察的拒绝结果；
- 同一个 job 不允许被两个 worker 同时执行。

必须提前承认三个崩溃窗口：

```text
Job 已插入 PENDING，尚未提交线程池时宕机
已进入 JVM 内存队列，worker 尚未执行时宕机
已写 RUNNING，执行中宕机
```

数据库记录只证明“工作单存在”。第一版若没有启动恢复扫描，PENDING/RUNNING
可能永久遗留；这正是以后升级可靠队列的依据。

## 2. 第 1 日：线程、任务和线程池分别是什么

### 根问题

> 代码提交给线程池后，究竟是什么在排队，什么在执行？

### 静态图

| 角色 | 作用 |
|---|---|
| `Runnable/Callable` | 一张待执行工作单 |
| 阻塞队列 | 暂时保存等候的工作单 |
| Worker Thread | 从队列取工作单并运行 |
| Executor | 接收任务、管理线程和队列 |
| Future | 调用方观察异步结果的句柄 |

### 最小手算

线程池：

```text
corePoolSize = 2
maxPoolSize = 4
queueCapacity = 3
```

提交 8 个长任务时，按当前执行器策略预测：

```text
先创建几个核心线程？
多少进入队列？
什么时候扩到最大线程？
第 8 个任务怎样处理？
```

注意不同 Executor 的入队/扩容策略可能不同；实验前先对照所用实现。

### Java 基础只学到够用

需要：

- `Runnable` 没有业务返回值；
- `Callable` 可以返回值并抛异常；
- `Future#get` 会等待；
- `CompletableFuture` 用阶段组合异步结果；
- `AtomicInteger` 适合简单原子计数，不替代业务事务；
- `CountDownLatch` 适合测试同时起跑和等待结束。

暂不展开 AQS、ForkJoinPool 源码。

## 4. 第 3 日：建立可查询异步 job

### 根问题

> 为什么不能直接 `@Async void doWork()` 后就算完成？

因为调用方至少需要知道：

```text
任务是否被接收
现在排队还是运行
是否成功
失败在哪里
是否可以重试
```

### 文件地图

```text
InternshipTaskJobDO
→ 保存 jobId、type、status、progress、errorMessage、requesterId

InternshipTaskJobMapper
→ 插入与条件更新状态

InternshipTaskJobService
→ 提交、查询、执行和状态机

InternshipTaskJobWorker
→ 真正在线程池 worker 中执行

InternshipTaskJobConfiguration
→ 明确容量、线程名、拒绝策略

Controller
→ POST /job/create，GET /job/get

Menu SQL
→ 注册 internship:task:job:create / job:query 权限资源
```

`@PreAuthorize` 中出现一个新权限字符串，并不会自动把它写进菜单表。集成接口时
同步更新 `sql/mysql/system_internship_task_menu.sql`，之后再由管理员给角色
授权；不要只用超级管理员测试，否则会掩盖普通角色持续 403 的缺口。

### 为什么 Executor 要拆成另一个 Bean

如果 Service 内部：

```java
this.executeAsync(jobId);
```

可能绕过 `@Async` 的 Spring 代理，变成当前线程同步执行。拆成另一个 Bean 后：

```text
Service
→ Executor 的 Spring 代理
→ 异步拦截器提交线程池
→ 原方法在线程池运行
```

1. 状态枚举；
2. 合法状态变化；
3. `createJob` 的人类逻辑；
4. `executeJob` 成功/失败后写什么；
5. 查询接口应该返回哪些状态字段。
6. 普通用户是否只能查询自己提交的 job。

## 5. 第 4 日：异常和拒绝不能消失

### 三种失败

#### 提交前失败

参数或权限不合法：

```text
不创建 job
→ HTTP 直接失败
```

#### 提交时被线程池拒绝

可选策略：

```text
方案 A：数据库 job 标记 REJECTED，仍返回 jobId，调用者可查询 rejected 状态
方案 B：接口返回系统繁忙，不创建用户可见 job，只记录指标/审计
```

第一版推荐 A，便于观察容量不足；不能“保存一条用户看不见的 REJECTED，又只
抛异常不给 jobId”，否则该记录只是运维证据，不是调用者契约。

#### worker 执行失败

```text
捕获业务异常
→ job 标记 FAILED
→ 保存短错误码/摘要
→ 完整堆栈进入日志
```

不要把敏感请求或 Token 写入 errorMessage。

### `void` 与 `Future`

`@Async void` 的异常无法通过调用返回值交给原调用方，需要：

- 方法内部落库并记录；
- 或统一 `AsyncUncaughtExceptionHandler`；
- 或返回 `CompletableFuture` 让上层组合/观察。

本业务以数据库 job 状态为真实结果，不依赖 HTTP 线程等待 Future。

### 故障实验

人工让第 3 个任务抛异常：

```text
前两个 SUCCESS
第三个 FAILED
后续任务仍可执行
线程池没有因一个异常整体死亡
```

## 6. 第 5 日：上下文为什么在线程切换后丢失

### 根问题

> `SecurityContext`、tenantId 原来在线程变量里，换 worker 后为什么不自动存在？

普通 `ThreadLocal`：

```text
请求线程 A 的 Map 中保存 user/tenant
→ worker 线程 B 有自己的 Map
→ B 默认看不到 A 的值
```

Yudao 的租户上下文使用 `TransmittableThreadLocal`；安全自动配置还把
`SecurityContextHolder` 的策略替换为
`TransmittableThreadLocalSecurityContextHolderStrategy`。配合线程池
`TaskDecorator`，两者都可以在“提交任务时”复制到 worker。

但这只是当前 JVM 中的一次上下文快照，不是长期可靠业务身份：应用重启、任务
重新调度或跨服务后不能假设它还在。

### 风险

- 线程复用后旧上下文未清理会串用户；
- 任务在没有请求上下文的 job 中执行时不能假设一定有登录人；
- 长期后台任务应把必要业务身份显式保存进 job，而不是永远依赖请求线程；
- 权限检查发生在提交阶段还是执行阶段，需要明确。

### 本业务选择

```text
提交阶段：
校验当前用户是否允许创建 job
→ 将 requesterUserId、tenantId 作为明确字段写入 job

执行阶段：
使用 job 中的业务上下文
→ 不把过期 access token 长期保存进数据库
```

如果执行阶段还需调用受权限保护的远程 API，应设计服务身份或短期凭证，不偷偷复用用户的旧 Token。

### 实验

记录请求线程和 worker 线程：

```text
thread name
userId
tenantId
traceId
```

确认哪些由 TTL 传播，哪些由 job 显式字段恢复。

## 7. 第 6 日：压力与容量

### 实验组

核心只提交一组：

```text
10～20 个任务
```

每个任务模拟 200～500ms 工作，记录：

```text
接受数
拒绝数
队列峰值
总耗时
```

100/1000 任务、内存、平均等待时间和活跃线程峰值属于 OPTIONAL；只有提供
明确采集代码后再做，避免把一天变成压测工具支线。

### 线程越多不一定越快

CPU 密集：

- 线程过多带来切换；
- 接近 CPU 核心数开始估算。

IO 密集：

- 等待期间可运行其他任务；
- 可以更多线程，但受数据库连接、远端限流和内存约束。

本业务如果每个 worker 都查数据库：

```text
线程池 max = 100
数据库连接池 max = 20
```

多出来的线程只会排队抢连接，不能凭空增加数据库吞吐。

### 参数不是背公式

先用测量选择：

```text
任务到达速率
平均执行时长
可接受等待时间
下游并发上限
进程资源
```

再设置 core/max/queue，并通过拒绝实验验证。

## 8. 第 7 日：收口与 Agent 连接

### Agent 只开放什么

第二圈暂时开放只读：

```text
query_job_status(jobId)
```

可选低风险写工具：

```text
create_report_job(filters)
```

开放写工具前必须具备：

- 当前用户确认；
- 幂等键；
- 明确任务类型白名单；
- job 状态可查询；
- 最大任务量；
- 审计记录；
- 不由模型直接选择任意类名或脚本。

### 回归矩阵

| 场景 | 预期 |
|---|---|
| 正常提交 | 快速返回 jobId |
| 后台成功 | PENDING→RUNNING→SUCCESS |
| 后台异常 | FAILED + 可观察错误 |
| 队列满 | 明确拒绝，不假成功 |
| 重复执行同一 job | 条件更新阻止双执行 |
| 进程重启 | 明确哪些 PENDING 需要恢复 |
| 无权限提交 | 不创建 job |
| 普通用户枚举别人的 jobId | 拒绝或返回不存在 |
| 上下文切换 | user/tenant 不串线 |

### 进入第 9 步门槛

- 能用“订单—队列—厨师”模型解释线程池并指出比喻边界；
- 能说出 core/max/queue/rejection 分别控制什么；
- 有一个真实 job 状态机；
- 观察过成功、worker 失败和队列拒绝；
- 能解释 ThreadLocal 为什么会丢、TTL 解决什么而不解决什么；
- 知道进程内队列不等于可靠消息队列。
