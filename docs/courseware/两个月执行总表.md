# 两个月执行总表

> 目标：用约 8 周、34 个核心 Session，完成第 6B～10 步的一条连续工程链。
> 业务主线：把现有“实习任务台账”逐步升级成能查询、认领、异步处理、防重复并发布事件的系统。

`Session` 是一张可独立验收的课程卡，不强制等于一个自然日。状态：

```text
CORE：两个月主线必须完成
OPTIONAL：有余力再做，或与相邻 Session 合并
```

## 1. 两个月后的目标画像

两个月后不要求成为分布式系统专家，也不要求写出复杂多 Agent。需要真正拥有以下能力：

```text
把自然语言能力变成受控工具契约
→ 用事务和原子 SQL 保护核心状态
→ 把慢任务放进有边界的线程池
→ 区分锁、幂等和限流
→ 用消息把非核心副作用从主流程拆开
→ 为每条链设计正常、失败和重复执行证据
→ 能让 AI 施工，但自己审查边界和结果
```

## 3. 连续业务演化

### 第 6B 步：只读查询

```text
自然语言问题
→ query_internship_tasks
→ Gateway / 权限 / Service / Mapper
→ 数据库事实
→ 模型回答
```

新增复杂度只有“模型选择工具”，不修改原业务状态。

### 第 7 步：并发认领

```text
用户点击认领
→ 检查 TODO
→ 原子地写入 assigneeUserId 并改为 IN_PROGRESS
→ 写认领记录
```

核心不变量：

```text
一个任务最多一个认领人
认领成功和认领记录要么都存在，要么都不存在
```

### 第 8 步：异步处理任务

```text
提交批量处理请求
→ 创建 job(PENDING)
→ 立即返回 jobId
→ 线程池执行
→ RUNNING
→ SUCCESS / FAILED
```

核心不变量：

```text
HTTP 返回不代表后台成功
任务状态必须可查询
异常不能只消失在线程日志里
```

### 第 9 步：Redis 保护入口

```text
同一请求重复提交 → 幂等
同一任务同时操作 → 锁或数据库原子条件
同一用户短时高频请求 → 限流
```

核心不变量：

```text
三种机制解决三种不同问题，不能看见 Redis 就混用
数据库仍是长期业务事实来源
```

### 第 10 步：任务事件

```text
认领/完成事务成功
→ 发布 TaskStatusChangedEvent
→ 消费者写审计或发送通知
```

核心不变量：

```text
核心状态更新不能依赖通知成功
消费者重复收到消息不能产生重复业务结果
失败消息必须可观察；核心版要明确一次重投与永久失败治理缺口
```

## 4. 每阶段的掌握深度

| 阶段 | 必须亲手 | 可以读懂即可 | 暂不学 |

## 5. 每周只固定回答三个问题

1. 本周保护的业务不变量是什么？
2. 用一条正常/失败时间线证明了什么，真实状态归谁？
3. 换成另一个业务后，哪些设计仍然保留？

“AI 最可能写错哪里”“各存储分别看到什么”作为导师追问，只在已有运行证据
后出现，不一次抛成问卷。

## 6. 可变节奏，不可变门槛

时间可以压缩，下面门槛不能省：

```text
一张静态责任图
一段能按时间执行的人类逻辑伪代码
一处代表性真实代码
一个正常实验
一个失败或重复实验
一条向上抽象的结论
```

## 7. 第 8 周后的选择

完成并通过冷启动复述后，再决定：

```text
路线 A：进入第 11 步微服务完整链路
路线 B：先做一次 6B～10 综合作品和求职材料
路线 C：若事务/并发证据仍薄弱，回补第 7～9 步
```

第 12～15 步不按日历自动开启，必须满足对应准入条件。
