# Yudao 后端 + Agent 学习架构

> 目标：不是把 Yudao 所有源码逐行看完，而是先形成可就业的小闭环，再逐步扩成能独立负责模块的工程闭环，最后形成后端 + Agent 的完整作品闭环。

---

## 一、总原则

### 1. 学习顺序

```text
先能找工作
→ 再能独立负责普通模块
→ 再处理并发、性能与分布式问题
→ 最后扩展成生产级 Agent 系统
```

### 2. 每一个知识点都按同一个方式学习

```text
找到真实业务
→ 追通链路
→ 亲手修改
→ 故意制造错误
→ 定位问题
→ 修复并验证
→ 整理笔记
→ 提交代码
```

### 3. 不以“看了多少源码”判断是否完成

完成标准始终是：

```text
能解释
→ 能修改
→ 能排错
→ 能迁移到自己的项目
```

### 4. 数据治理业务只作为渐进语境

数据治理业务语境不会把当前阶段改造成数据中台课程，也不会因为“贴近真实业务”就提前加入 DataX、Flink、Kafka、元数据和数据质量等实现。

采用下面的轻量旁线：

```text
当前 Java 后端主线
→ 顺带认识 1 个相关的数据治理概念
→ 只理解它的位置、输入输出和 Java 边界
→ 用当前小例子建立类比
→ 有真实实现需求时再深入
```

详细映射见：[数据治理概念渐进融入路线](数据治理概念渐进融入路线.md)。

## 第 4 步：登录、Token、权限与 Redis

### 核心问题

```text
用户如何登录？
Token 如何生成和保存？
Axios 为什么会自动携带 Token？
后端如何识别当前用户？
为什么有的接口返回 401，有的返回 403？
```

### 学习主线

```text
登录页面
→ 登录 API
→ 用户名密码校验
→ access token / refresh token
→ 前端保存 Token
→ Axios 请求拦截器
→ Authorization 请求头
→ Security Filter
→ 当前登录用户
→ @PreAuthorize
→ 用户、角色、权限
→ Redis 登录状态
```

### 实战任务

1. 在 Network 中完整观察一次登录。
2. 找到前端保存 Token 和读取 Token 的代码。
3. 追通后端登录 Controller、Service、密码校验和 Token 创建。
4. 追通 `/system/user/page` 的认证与权限检查。
5. 在 Redis 中观察登录、退出前后的 Key 和 TTL。
6. 创建一个只允许查询用户、不能新增和删除用户的测试角色。

### 完成标准

能够独立解释：

- access token 与 refresh token 的区别
- Token 如何进入每一次 HTTP 请求
- 后端如何从 Token 识别用户
- 用户、角色、菜单权限如何关联
- `@PreAuthorize` 如何决定放行
- Redis 在登录体系中保存了什么
- 401 与 403 的区别

## 第 5 步：独立完成一个小业务模块

> 这一项比立即深挖微服务更重要。它决定你是否从“会跟代码”进入“能独立开发”。

详细执行计划见：[第 5 步：独立业务模块学习计划](../stages/第5步-独立业务模块学习计划.md)。

### 本阶段的关键调整

第 4 步证明了架构下钻是必要的，但模块和组件过多时，不能把“全部读完”当成完成标准。第 5 步采用受控纵向切片：

```text
先做业务模型
→ 画页面到数据库的整体链路
→ 每轮只实现一个可验证切片
→ 默认只向下钻一层
→ 细节只在影响业务规则、状态、信任、持久化或失败时进入
→ 每轮结束回到整体图复述
```

第一版不新建独立微服务，而是在现有 `system-server` 中实现边界清楚的业务包；新服务注册、Gateway 路由和 Feign 留到第 11 步。

### 推荐模块

优先选择与自己真实需求相关的一个：

- 实习任务管理
- 会议纪要管理
- 科研论文订阅管理
- 知识库标签管理
- 文档处理任务管理

建议第一版使用“实习任务管理”。

当前确定第一版为“后台实习任务台账”，不加入任务分派、个人数据范围、提醒和审批。

它不会改名为“数据治理任务”，也不增加大数据字段。第 5 步只顺带建立一个迁移抓手：普通任务台账与未来数据处理管理端都会遇到“任务定义、状态、权限和失败结果”，但真正搬运或计算数据的是外部执行引擎。第一版只理解这个边界，不调用 DataX、Flink 等组件。

### 最小功能

```text
任务列表
新增任务
编辑任务
删除任务
状态切换
按标题、状态、时间筛选

```

### 需要独立完成

```text

Controller
ReqVO / RespVO

菜单

```

### 学习量预算

```text
每轮 1 个根问题
第一遍最多 5 个核心文件
只参考 1 个相似模块：通知公告
一个解释簇默认只下钻 1 层
最多保留 2 个支线，其余进入停车场
每轮至少留下 1 个运行或测试证据
```

完成当前层的判断标准：能说明调用者、职责、输入输出，以及正常和一个失败分支；不要求逐行读完所有父类、工具方法、自动配置和缓存实现。

### 完成标准

没有人告诉你具体文件时，你能够：

1. 自己设计表结构。
2. 自己定位项目中类似模块作为参考。
3. 独立完成前后端。
4. 处理参数校验和异常。
5. 添加权限。
6. 完成基础测试。
7. 写出清晰的提交说明。
8. 能区分入口、运输、业务决策、状态存储和展示层。
9. 能说明哪些细节被有意识地暂缓，以及未来扩展会改变哪一层。

# 七、如何判断自己真的掌握

对任何一个主题，依次通过四级测试。

## 1. 能解释

不看笔记说明：

```text
输入是什么
经过哪些层
输出是什么
为什么这样设计
```

## 2. 能修改

只给业务目标，不告诉文件路径，你能完成改动。

## 3. 能排错

故意制造错误后，你能通过：

```text
Network
日志
断点
SQL
Redis
线程栈
监控
```

找到问题。

## 4. 能迁移

脱离 Yudao，在自己的项目中重新实现类似功能。

达到第 4 级，才算真正掌握。
