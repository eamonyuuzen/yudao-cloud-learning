# Yudao 后端 + Agent 学习架构

> 目标：不是把 Yudao 所有源码逐行看完，也不是把某个 Agent 框架当终点；而是逐步成为能定义业务问题、借助 AI 施工、审查验证结果并对系统交付负责的 AI 原生后端工程师。

---

## 一、总原则

### 1. 学习顺序

```text
先能开发并交付一个普通业务闭环
→ 再能借助 AI 独立负责普通模块
→ 再处理并发、性能与分布式问题
→ 最后把后端、数据治理语境与受控 AI 能力整合成可靠系统
```

### 2. 先判断知识类型，再决定学习深度

```text
查用型：注解、API、命令和重复配置
→ 知道作用、位置、怎样查询和验证，不背内部源码

机制型：调用链、生命周期、数据流和失败路径
→ 用一条代表性链路跑通正常与失败分支，再向上抽象

决策型：业务规则、状态、权限、数据安全、接口契约和验收标准
→ 用户亲自建模和判断，AI 可以施工，但结果必须由用户审查和验证

底层实现：框架、JDK、容器或操作系统内部
→ 只在真实排错、性能、安全或扩展需要时下钻
```

### 3. 不以“看了多少源码”判断是否完成

完成标准始终是：

```text
能定义问题和完成边界
→ 能解释关键机制
→ 能指挥并审查实现
→ 能用证据验证
→ 能排错
→ 能迁移到自己的项目
```

### 4. 数据治理业务只作为渐进语境

数据治理业务语境不会把当前阶段改造成数据中台课程，也不会因为“贴近真实业务”就提前加入 DataX、Flink、Kafka、元数据和数据质量等实现。

采用下面的轻量旁线：

```text
当前 Java 后端主线
→ 顺带认识 1 个相关的数据治理概念
→ 只理解它的位置、输入输出和 Java 边界
→ 用当前小例子建立类比
→ 有真实实现需求时再深入
```

详细映射见：[数据治理概念渐进融入路线](数据治理概念渐进融入路线.md)。

## 第 4 步：登录、Token、权限与 Redis

### 核心问题

```text
用户如何登录？
Token 如何生成和保存？
Axios 为什么会自动携带 Token？
后端如何识别当前用户？
为什么有的接口返回 401，有的返回 403？
```

### 学习主线

```text
登录页面
→ 登录 API
→ 用户名密码校验
→ access token / refresh token
→ 前端保存 Token
→ Axios 请求拦截器
→ Authorization 请求头
→ Security Filter
→ 当前登录用户
→ @PreAuthorize
→ 用户、角色、权限
→ Redis 登录状态
```

### 实战任务

1. 在 Network 中完整观察一次登录。
2. 找到前端保存 Token 和读取 Token 的代码。
3. 追通后端登录 Controller、Service、密码校验和 Token 创建。
4. 追通 `/system/user/page` 的认证与权限检查。
5. 在 Redis 中观察登录、退出前后的 Key 和 TTL。
6. 创建一个只允许查询用户、不能新增和删除用户的测试角色。

### 完成标准

能够独立解释：

- access token 与 refresh token 的区别
- Token 如何进入每一次 HTTP 请求
- 后端如何从 Token 识别用户
- 用户、角色、菜单权限如何关联
- `@PreAuthorize` 如何决定放行
- Redis 在登录体系中保存了什么
- 401 与 403 的区别

## 第 5 步：独立完成一个小业务模块

> 这一项比立即深挖微服务更重要。它决定你是否从“会跟代码”进入“能独立开发”。

详细执行计划见：[第 5 步：独立业务模块学习计划](../stages/第5步-独立业务模块学习计划.md)。

### 本阶段的关键调整

第 4 步证明了架构下钻是必要的，但模块和组件过多时，不能把“全部读完”当成完成标准。第 5 步采用受控纵向切片：

```text
先做业务模型
→ 画页面到数据库的整体链路
→ 每轮只实现一个可验证切片
→ 默认只向下钻一层
→ 细节只在影响业务规则、状态、信任、持久化或失败时进入
→ 每轮结束回到整体图复述
```

第一版不新建独立微服务，而是在现有 `system-server` 中实现边界清楚的业务包；新服务注册、Gateway 路由和 Feign 留到第 11 步。

### 推荐模块

优先选择与自己真实需求相关的一个：

- 实习任务管理
- 会议纪要管理
- 科研论文订阅管理
- 知识库标签管理
- 文档处理任务管理

建议第一版使用“实习任务管理”。

当前确定第一版为“后台实习任务台账”，不加入任务分派、个人数据范围、提醒和审批。

它不会改名为“数据治理任务”，也不增加大数据字段。第 5 步只顺带建立一个迁移抓手：普通任务台账与未来数据处理管理端都会遇到“任务定义、状态、权限和失败结果”，但真正搬运或计算数据的是外部执行引擎。第一版只理解这个边界，不调用 DataX、Flink 等组件。

## 第 6B 步：最小 Agent 业务闭环

> 暂时不做复杂 MCP、多 Agent、写操作和审批流程。

技术路线不做 Java / Python 二选一：

```text
先用 Yudao 现有 Spring AI 跑通 Java 原生参考闭环
→ 再用最小 Python Agent 服务通过 HTTP + Authorization 调用 Java 业务接口
→ Java 继续拥有身份、权限、规则和数据
→ Python 只承担模型接入与编排迁移练习
```

笔记本默认使用云端模型 API；台式机后续用 Ollama 提供可替换的本地模型 API。模型位置变化不应改变工具契约和 Java 业务接口。

当前路线已根据 2026-08-01 的技术状态收敛：

```text
先写出框架无关的工具循环伪代码
→ 用 Pi Agent Core 限时阅读一条透明的运行时源码链
→ 跑通 Yudao 现有 Spring AI 1.1.5 Java 工具
→ 审查 ToolContext、内部 API 与权限边界
→ 用 Python Agent 通过 Gateway + Authorization
   调用现有实习任务分页接口
→ 用固定案例检查调用轨迹和最终数据库结果
```

Pi 不作为第二套业务实现：它只替代“Agent Runner/运行时”这个
可替换层的源码样本。当前 Python Lab 继续承担跨语言业务闭环；
Java 继续承担身份、权限、规则和数据事实。这样既能看懂框架内部，
又不会因同时切换 Python/TypeScript 而丢失业务主线。

Spring AI 2.0.0 已经 GA，但当前项目是 Spring Boot 3.5.15 + Spring AI 1.1.5。本阶段只理解 2.0 的推荐演进方向，不做版本迁移。Agent 的详细学习边界和施工步骤见：

- [第 6B 步：最小 Agent 业务闭环学习工作台](../stages/第6B步-最小Agent业务闭环学习工作台.md)
- [第 6B 步：逐轮执行包与可运行 Lab](../courseware/stages/第6B步-Agent逐轮执行包.md)

# 七、如何判断应该学多深、是否真的掌握

先判断当前知识需要到哪一层：

```text
黑盒层：知道所有者、输入、输出和作用
机制层：能跑通一次真实事件，说明状态、匹配、正常和失败分支
实现层：能定位具体代码、修改契约、审查差异并处理异常
```

不是所有主题都要求实现层。框架语法通常到黑盒或机制层；业务规则、状态、权限、数据安全和失败恢复应进入实现与责任层。

“已掌握”至少需要：

```text
不看笔记复述核心模型
→ 给出一个正常分支和一个失败分支
→ 用源码、测试、HTTP、日志或数据库事实形成证据
→ 隔一段时间仍能重新定位
→ 能完成修改、排错或跨项目迁移中的至少一项
```

AI 可以完成大部分机械代码，但用户必须能够说明：

```text
为什么这样做
→ 它保护了什么规则
→ AI 可能在哪里写错
→ 用什么证据验收
→ 出现故障先检查哪一层
```

一次听懂、一次生成成功或一次绿色测试，只能算当前证据，不能自动标记为长期掌握。
