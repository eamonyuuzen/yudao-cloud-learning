# 数据治理概念渐进融入路线

> 目标：不把当前 Yudao 主线改造成大数据课程，而是在普通 Java 后端学习中，逐步建立对数据治理平台的方位感。

## 1. 总体策略

```text
Java 后端主线照常完成
→ 每个阶段只挂接 1 个最相关的数据治理概念
→ 先用生活比喻建立位置感
→ 只回答它的输入、输出、状态和 Java 边界
→ 当前实现真的依赖它时，才学习组件和源码
```

这条路线不是第二套并行课程。数据治理概念只是一层“业务语境”，不能挤占当前纵向切片。

### 每张概念卡的固定上限

第一遍只回答五点：

```text
它解决什么问题？
它在整条数据链路的什么位置？
输入和输出是什么？
Java 管理端对它做什么？
当前阶段暂时不学什么？
```

默认最多使用一个比喻、一个小例子，不打开大数据组件源码。

## 2. 三层认知深度

### A. 耳熟层

能听懂词语，大致知道位于哪一段。例如听到 DataX，知道它偏向批量搬运数据，而不是后台 CRUD 框架。

### B. 接口层

能说清 Java 后端如何配置、触发、查询状态和处理失败，但不要求理解执行引擎内部算法。

### C. 实现层

只有真实工作或当前实验需要时，才进入部署、性能、容错和底层原理。

当前优先达到 A，少数与 Java 工作直接相关的内容达到 B；不提前追求 C。

## 3. 贯穿后续步骤的概念卡

| Yudao 主线 | 顺带认识的数据治理概念 | 第一比喻 | 本阶段只理解 | 暂不深入 |
|---|---|---|---|---|
| 第 5 步：独立 CRUD 与状态 | 管理端与执行引擎 | 调度室填写任务单，施工队真正施工 | 任务定义、状态、操作权限与执行结果是不同责任 | DataX/Flink 的运行原理 |
| 第 6A 步：测试、部署、排错 | 数据任务的可运行性 | 不只会填任务单，还要确认施工队能启动、日志能找到 | 配置、环境、日志、失败定位 | 大数据集群部署 |
| 第 6B 步：最小 Agent | 数据目录与只读数据服务 | 图书管理员先查目录，再决定去哪取书 | Agent 通过受控 API 查询目录或状态 | Agent 直接操作数据仓库 |
| 第 7 步：事务与并发 | 治理规则配置的一致性 | 一套规则要整套生效，不能只改一半 | 配置表和关联表为何需要事务、唯一约束 | 分布式计算事务 |
| 第 8 步：异步与线程池 | 数据探查/集成任务 | 前台登记后返回任务号，后台慢慢执行 | 提交、排队、运行、成功、失败 | Spark/Flink 计算模型 |
| 第 9 步：Redis、幂等、限流 | 防止重复触发与状态缓存 | 同一张施工单不能重复开工 | 任务幂等、缓存状态与数据库真相源 | 分布式缓存复杂治理 |
| 第 10 步：消息队列 | 任务状态事件 | 施工完成后广播“已完工”，订阅者各自处理 | 事件、重复消费、重试和审计 | Kafka 分区与存储底层 |
| 第 11 步：微服务调用 | Java 管理端调用数据组件 | 调度中心通过工单/API 指挥专业设备 | 配置、触发、查询、停止和错误适配 | 自己实现 DataX/Flink |
| 第 12 步：高并发 | 数据服务 API 的配额与 SLA | 对外窗口要控制排队人数和服务承诺 | 限流、配额、超时、热点查询 | 大规模数仓调优 |
| 第 13 步：性能与可观测性 | 元数据检索和任务监控 | 查目录要快，执行过程要留轨迹 | 索引、日志、指标、traceId | Elasticsearch/Kylin 深层原理 |
| 第 14 步：可靠性 | 配置状态与执行状态一致性 | 调度室写着完成，不代表现场真的完成 | 超时、未知结果、重试、补偿、对账 | 完整数据中台容灾 |
| 第 15 步：Agent/MCP | 数据资产助手 | 先查目录和权限，再提供可追溯结果 | 只读检索、权限、审计、人工确认 | 自治修改生产数据 |

## 4. 第一批基础词汇

这些词只建立“人类逻辑”，不要求背产品细节。

### 元数据：数据的说明书

```text
真正的数据：一行客户记录
元数据：它属于哪张表、有哪些字段、字段是什么类型、谁负责、什么时候更新
```

类似图书馆的目录卡。目录不是书的正文，但没有目录就很难管理和找到书。

### 数据标准：大家共同使用的填写规则

例如不同系统都表示“性别”，但编码可能分别是 `男/女`、`1/2`、`M/F`。数据标准规定统一含义和表达方式。

### 数据质量规则：针对数据的自动检查

它有点像参数校验和测试规则：手机号不能为空、身份证格式正确、某字段取值必须在允许范围内。区别是检查对象从一次 HTTP 请求扩大成数据表或数据集。

### ETL：取出、整理、放入

```text
Extract：从来源取数据
Transform：清洗、转换、标准化
Load：写入目标位置
```

可以把它理解为搬家：先从旧房取东西，途中分类清理，最后放到新房的正确位置。

### 数据血缘：数据的来路和去向

类似快递轨迹或食品溯源：这个字段从哪个系统来，经过哪些转换，最后被哪些报表和接口使用。

### 数据资产目录：可以被发现和申请的数据清单

它不是把所有真实数据直接展示出来，而是告诉使用者“有什么、由谁负责、如何申请、能否访问”。

## 5. 第 5 步的实际用法

第 5 步仍实现“后台实习任务台账”，不增加数据源、ETL、元数据、质量规则等字段。

只借用一组认知对照：

```text
实习任务台账
→ 保存任务说明、状态和操作权限

未来的数据处理管理端
→ 保存数据任务定义、调度配置、执行状态和操作权限

真正的数据处理引擎
→ 根据配置去搬运或计算数据
```

两者复用的是“管理对象 + 状态流转 + 权限 + 失败结果”这一类 Java 后端范式，不是业务字段完全相同。

第 5 步结束时，只增加一个迁移问题：

> 如果当前任务不是由人手动完成，而是交给外部执行引擎，现有 Controller、Service、任务状态和错误处理分别会发生什么变化？

能够说出大致变化即可，不实现。

## 6. 第 6 步的实际挂接点

第 6 步不新增数据治理业务功能，只借当前工程证据认识五个位置：

```text
Service / Controller 测试
→ 类比数据质量规则：规则必须能够自动发现不合格结果

部署、依赖和健康检查
→ 类比数据任务可运行性：配置存在不等于任务真正能运行

日志、HTTP 和故障轨迹
→ 类比任务审计：谁在什么时候执行了什么，结果怎样

Agent 工具描述和只读查询
→ 类比数据资产目录和数据服务：先告诉使用者有什么，再通过受控接口读取

工具 → Java API → 数据库 → 回答
→ 类比简化数据血缘：结果从哪里来，经过哪些转换，最终被谁使用
```

第 6 步结束时只回答一个迁移问题：

> 如果 Agent 查询的不是系统用户，而是公司数据资产目录，元数据、权限、数据范围、审计和真实数据分别应由谁负责？

能画出责任边界即可，不实现元数据平台、ETL、数据质量引擎或数据仓库。

## 7. 防止概念渗透变成主线膨胀

出现以下任一情况，立即把数据治理问题放回停车场：

- 为理解一个普通 CRUD，开始连续解释三个以上大数据组件；
- 当前没有真实调用，却开始研究组件部署和底层算法；
- 为了“贴近真实业务”而不断给第一版增加字段、表和微服务；
- 新概念不能帮助解释当前对象、状态、边界或失败；
- 用户已经记住很多名词，但说不清当前请求怎样进入数据库。

每个阶段结束后再判断：概念只是耳熟、已经理解接口边界，还是有真实证据值得继续深入。
