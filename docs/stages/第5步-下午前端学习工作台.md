## 1. 下午唯一主问题

```text
用户在页面上查询、创建或推动任务状态时，
一个页面动作怎样变成后端请求，

```

先使用这张粗模型导航：

```text

→ Vue 页面保存交互状态
```

## 3. 只让用户补全三个关键点

### 补全点 1：分页结果进入页面状态

位置：`views/internship/task/index.vue` 的 `getList`。

人类逻辑：

```text
拿当前 queryParams 请求分页
→ 得到 { list, total }
→ list 交给表格
→ total 交给分页器
```

学习目标不是记三行语法，而是识别：

```text
queryParams
→ 页面拥有的查询输入状态

list / total
→ 页面拥有的展示结果状态

API
→ 输入状态和后端之间的运输边界
```

### 补全点 2：状态动作

位置：`index.vue` 的 `handleUpdateStatus`。

人类逻辑：

```text
用户确认
→ 页面发送 id + 目标状态
→ 后端判断迁移是否合法
→ 成功则提示并重新查询
→ 失败则由 Axios 通用层展示后端错误
```

关键边界：

> 前端按钮可以减少错误操作，但不能成为状态规则的最终裁判。

### 补全点 3：新增/编辑表单复用

位置：`InternshipTaskForm.vue` 的 `submitForm`。

人类逻辑：

```text
先做前端格式校验
→ formType 是 create：调用新增
→ formType 是 update：调用修改
→ 成功后关闭弹窗
→ emit success 通知父页面重新查询
```

这里要看懂两个方向：

```text
父页面 → 子表单
ref + defineExpose(open)

子表单 → 父页面
emit('success') + @success="getList"
```

## 4. 学习深度控制

### 必须真正理解

- TypeScript 接口为什么对齐 ReqVO / RespVO，而不是数据库 DO；
- GET 的查询条件放 `params`，JSON 请求体放 `data`；
- 为什么 `update-status` 必须根据后端 `@RequestBody` 使用 `data`；
- `queryParams → API → list/total` 的单向数据流；
- 页面状态、后端业务状态和数据库事实不是同一个东西；
- 父子组件如何通过 `open` 和 `success` 协作；
- 前端校验、后端业务校验各自守什么边界。

### 能认出作用即可

- `ref`：保存一个需要响应式更新的值；
- `reactive`：保存一组响应式字段；
- `v-model`：输入组件与页面状态双向绑定；
- `onMounted`：页面首次挂载后查询；
- `async/await`：等待 API Promise；
- `try/finally`：无论成功失败都关闭 loading；
- `defineExpose / defineEmits`：父子组件通信的两个方向。

### 本轮当作黑盒

- Element Plus 每个组件的全部属性；
- UnoCSS 类名和页面美化；
- Vue 编译器、虚拟 DOM、响应式底层实现；
- Axios 拦截器内部细节；
- Vite 插件和自动导入原理；
- 字典管理系统、国际化系统；
- TypeScript 高级类型体操。

## 5. 一个重要的接口设计对比

不能机械复制已有模块：

```text
某些已有 update-status 接口
→ 后端用 @RequestParam
→ 前端使用 params

本次实习任务 update-status
→ 后端用 @RequestBody UpdateStatusReqVO
→ 前端必须使用 data
```

真正应当复制的是“接口契约对齐”的原则，不是某一行 Axios 写法。
