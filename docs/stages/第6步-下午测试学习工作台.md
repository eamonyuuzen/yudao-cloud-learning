## 1. 下午唯一主问题

```text
同一条实习任务业务，
为什么需要 Service 数据库测试、Controller 测试和真实 HTTP 验证，
它们各自能证明哪一段，又漏掉哪一段？
```

先用一张证据地图导航：

```text
Service 数据库测试
→ 证明业务规则 + Mapper + SQL / H2

Controller 测试
→ 证明 HTTP 参数绑定 + Validation + Controller 契约

带方法安全的接口测试
→ 再证明 SecurityContext + @PreAuthorize

真实 HTTP 冒烟
→ 证明网关、真实服务、真实配置与依赖能够连起来
```

测试不是越靠外越“高级”，而是观察范围不同。越靠外覆盖越完整，失败原因也越多；越靠内定位越精确，遗漏的系统边界也越多。

## 3. 下午的三个学习点

### 学习点一：读懂一个现有测试的 Arrange / Act / Assert

只选 `testUpdateInternshipTaskStatus_invalidTransition`：

```text
Arrange：数据库先有一条 TODO 任务
Act：请求直接跳到 DONE
Assert：
  业务异常必须出现
  数据库状态仍然是 TODO
```

重点不是背 `@Test` 和断言函数，而是看见：

```text
输入事实
→ 执行动作
→ 可观察结果
```

### 学习点二：设计一个 Controller 参数错误案例

先由用户判断：

```text
发送一个缺少 title 的新增请求
→ 应该在哪一层被拒绝？
→ Service 应不应该执行？
→ 数据库应不应该新增？
→ 最直接的证据是什么？
```

AI 负责准备重复脚手架和运行命令；用户保留测试输入、预期结果和关键断言。

### 学习点三：把“参数错误”和“无权限”分开

```text
参数错误
→ 请求格式或字段不满足 Controller 契约
→ 重点看 400 类响应和 Validation

无权限
→ 参数可以完全正确，但当前 LoginUser 没有对应 permission
→ 重点看方法安全和 403
```

下午只把两种失败画清并完成其中一个自动化证据；若环境顺利，再补另一个。真实网关 403 留到下一轮也不影响今天完成测试证据图。

## 6. 学习深度

必须掌握：

- 测试先声明“我要证明哪一段”，再决定测试类型；
- Arrange / Act / Assert 是测试的最小人类逻辑；
- Mock 是替身，不是更假的代码，而是主动缩小证据范围；
- H2 证明数据库交互逻辑，不等于证明生产 MySQL 环境；
- Controller 参数校验与 Service 业务规则是两道不同防线；
- 方法权限不能只背静态角色；要能动态模拟一次调用：启动装配先建立连接，运行时调用先到 Spring 代理，再按 `PreAuthorize.class` 匹配权限拦截器，最后放行或拒绝。

能够认出即可：

- `@Test` 标记测试入口；
- `@Import` 把少量真实 Bean 放进测试环境；
- `assertEquals` 比较实际结果和预期结果；
- `assertServiceException` 验证预期业务异常；
- Spring Test 为测试准备缩小后的容器。

本轮停车：

- JUnit 引擎怎样发现和调度测试；
- MockMvc 内部实现；
- Spring AOP 代理源码；
- 完整 JVM 类加载细节；
- 覆盖率、契约测试、性能测试和端到端平台。
