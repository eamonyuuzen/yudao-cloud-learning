# 第 6 步：测试、部署、排错与最小 Agent 学习计划

> 版本：v0.2，已纳入 3～4 天学习窗口、一周轻复习空窗、双电脑与 Java/Python Agent 路线。
> 当前入口：第 5 步独立业务纵向切片已经完成，从第 6A 步开始。
> 核心原则：先建立系统黑盒和责任边界，再进入一个具体机制；每轮至少留下一个可观察证据。

## 1. 第 6 步到底在解决什么

第 5 步证明了：

```text
我可以把一个业务需求
→ 建模
→ 写成前后端代码
→ 接入权限和数据库
→ 在开发环境中运行
```

第 6 步继续解决两个更接近真实工作的根问题：

```text
6A：
代码离开 IDE 后，怎样证明它能被测试、打包、运行、访问和排错？

6B：
怎样让大模型通过受控入口调用已有 Java 业务能力，
而不是绕开 Service、权限和数据边界直接操作数据库？
```

所以第 6 步不是一张技术名词清单，而是把能力从“会开发功能”推进到：

```text
会开发
→ 会证明
→ 会交付
→ 会定位故障
→ 会把既有业务能力安全地接给 Agent
```

## 2. 两个闭环的关系

### 6A：工程交付闭环

```text
源码
→ 自动化测试提供局部证据
→ 构建生成 JAR / dist
→ 配置和依赖组成运行环境
→ Java 进程与 Nginx 对外服务
→ 浏览器真实访问
→ 日志、端口、进程和请求帮助定位故障
```

一句话本质：

> 6A 学的不是“怎样敲部署命令”，而是一个系统从源码变成可运行服务时，产物、配置、进程、网络、依赖和证据之间怎样连接。

### 6B：最小 Agent 业务闭环

```text
用户自然语言
→ 模型理解意图并选择工具
→ 工具契约把意图变成确定参数
→ Java 工具调用已有 Service / API
→ 业务代码执行权限、规则和查询
→ 工具返回结构化结果
→ 模型组织成人类回答
```

一句话本质：

> Agent 是已有业务能力之上的新入口和协调者，不是第二套业务系统，也不应该跳过确定性的 Java 规则。

### 为什么先 6A、后 6B

Agent 增加了一个新的入口和故障边界。如果原有系统还不能稳定测试、部署和排错，再加入模型调用后，将很难区分问题来自：

```text
模型选择
工具参数
Java 业务
权限
数据库
配置
网络
部署环境
```

因此先完成 6A 的工程证据链，再进入 6B。

### Agent 技术路线：不做 Java / Python 二选一

当前推荐分成两个先后发生的学习层：

```text
第一层：Java 原生参考闭环
Yudao AI 模块 + Spring AI
→ 跑通项目已有工具
→ 复用现有 Service / API
→ 看清模型、工具和 Java 业务的最短链路

第二层：Python 跨语言迁移闭环
Python Agent 小服务
→ 调用云端或本地模型
→ 工具通过正常 HTTP + Authorization 调用 Java 接口
→ 不复制 Java 业务规则，不直连业务数据库
```

这不是维护两套业务实现：

```text
Java：
身份、权限、业务规则、数据范围、数据库和事实来源

Python：
模型接入、意图编排、工具选择和跨语言调用实验
```

第一版 Python 组件只使用：

```text
FastAPI：提供一个很小的 Agent HTTP 入口
Pydantic：约束请求、工具参数和响应结构
HTTP 客户端：携带正常 Authorization 调用 Java
模型 SDK：连接 OpenAI 兼容的云端或本地模型 API
pytest：验证工具参数和 Java API 适配
```

第一版只有单步或简单两步调用时，不立即加入 LangGraph。出现以下真实需要后再加入：

```text
多个节点和明确分支
需要保存中间状态
失败后恢复
人工确认
长时间运行
```

Spring AI 不是临时或不可用框架。它已经是 Spring 官方稳定项目，并原生提供模型抽象、工具调用、DeepSeek、Ollama 和 MCP 等能力。当前 Yudao 项目固定使用 `Spring AI 1.1.5`，本阶段以兼容现有项目为先，不为了追逐新版本直接升级到 2.0。

LangGraph 是偏底层的状态化编排运行时，适合持久化、恢复、人工介入和复杂流程；其官方文档也建议初学者先理解模型和工具。当前简单闭环若直接使用它，容易让框架结构抢走“模型为什么会调用工具”这个根问题。

### Java 框架选择：主线、对照与升级点

| 框架 | 核心长处 | 当前项目代价 | 第 6 步定位 |
|---|---|---|---|
| Spring AI | Spring 官方生态、模型抽象、`ChatClient`、Tool Calling、Spring Boot 自动配置 | 复杂 Agent 编排需要继续组合或引入上层框架 | 主线；项目已有 1.1.5 和完整工具基础 |
| LangChain4j | Java 原生、AI Services 接口代理、工具/RAG/结构化输出较完整，也可集成 Spring Boot | 会在同一项目引入第二套 AI 抽象，削弱现有源码复用 | 后续做一个很小的对照实验，不替换主线 |
| Spring AI Alibaba Agent/Graph | 在 Spring AI 上增加 State、Node、Edge、ReactAgent 和工作流/多 Agent 编排 | 概念密度更高，简单单工具场景容易过度设计 | 出现真实状态、分支、恢复或人工介入后再升级 |

当前框架决策：

```text
基础 Tool Calling：
使用 Spring AI

Java 中出现真实复杂工作流：
优先评估 Spring AI Alibaba Agent / Graph

需要比较另一种 Java 抽象：
用独立小样例体验 LangChain4j AI Services

需要跨语言和 Python 生态：
增加 Python 旁路服务，不替换 Java 业务核心
```

“中等难度起步”不等于一开始就使用复杂图框架。本阶段会直接观察 Spring AI 的 `ToolCallback`、`ToolCallingManager` 和工具执行循环，而不只调用一个完全隐藏细节的高级 Agent，因此仍然具有足够的机制学习深度。

## 3. 本阶段需要达到的抽象能力

完成第 6 步后，应能不依赖具体类名说明两种通用模型。

### 模型一：可运行服务模型

任何后端服务都可以先抽象为：

```text
构建输入：源码 + 依赖 + 构建配置
构建输出：可执行产物

运行输入：产物 + 运行配置 + 外部依赖
运行状态：进程 + 端口 + 连接 + 数据
运行输出：HTTP 响应 + 日志 + 状态变化

失败定位：
先判断失败在哪个边界
→ 再读取该边界最直接的证据
→ 最后进入具体代码或配置
```

### 模型二：受控 Agent 工具模型

任何业务工具都可以先抽象为：

```text
谁可以调用
→ 工具提供什么确定能力
→ 参数和返回值是什么
→ 哪些业务规则仍由 Java 决定
→ 工具失败时怎样返回
→ 哪些操作必须禁止或需要审批
```

最终不能只记住 `@Tool`，而要能判断：

```text
模型负责理解和选择
工具契约负责限制输入输出
Service 负责确定业务规则
数据库负责保存事实
权限和审计负责控制风险
```

## 4. 学习深度约定

### 4.1 测试

本阶段达到：

- 能区分单元测试、Service 数据库测试、Controller 测试和真实 HTTP 冒烟分别证明什么。
- 能读懂并编写少量代表性的 JUnit 测试。
- 能准备输入、调用真实目标、读取实际结果、断言正常与失败分支。
- 能理解 Spring 测试环境、H2、Mock 与真实依赖的证据边界。
- 能看到测试失败后，从失败案例定位到业务规则或环境边界。

暂不深入：

- JUnit 测试引擎内部实现。
- Spring Test 全部注解。
- 大规模 Mock 技巧、覆盖率指标竞赛和复杂测试架构。

### 4.2 部署和运行

本阶段达到：

- 能画出源码、JAR、dist、配置、进程、端口、MySQL、Redis、Nacos、Nginx 的关系。
- 能打包并在 IDE 外启动后端。
- 能构建前端并由 Nginx 提供静态页面。
- 能用 Docker Compose 管理本阶段需要的依赖服务。
- 能使用少量 Linux 命令查看文件、进程、端口、日志和容器状态。
- 能说明本机开发拓扑与真正多服务器部署在责任上的相同点和物理位置上的区别。

暂不深入：

- Linux 系统管理全套知识。
- Docker namespace、cgroup 和联合文件系统源码。
- 复杂镜像优化、Kubernetes、CI/CD。
- Nginx 性能调优、负载均衡、TLS 与生产级高可用。

### 4.3 排错

本阶段达到：

- 不把“报错很多”直接等同于“代码很多地方都坏了”。
- 先按浏览器、网关、服务、依赖、数据库、构建和配置划分故障边界。
- 能使用状态、日志、端口、HTTP 响应和数据库结果形成证据链。
- 能独立定位本阶段列出的常见故障，并说明为什么。

暂不深入：

- 完整可观测性平台。
- 分布式 Trace、指标告警体系和生产事故治理。

### 4.4 Agent

本阶段达到：

- 能解释自然语言如何经过模型、工具描述、参数、Java 方法和工具结果形成闭环。
- 跑通一个项目现有工具。
- 完成一个真实数据库的只读用户查询工具。
- 增加部门查询，并观察模型怎样进行两步工具调用。
- 能说明为什么工具应复用 Service / API，而不是直接连接数据库。
- 能识别参数校验、权限、数据范围、超时、空结果、错误返回和审计边界。

暂不深入：

- 写操作 Agent。
- MCP Server、多 Agent、复杂工作流和长期任务。
- 复杂 RAG、知识库平台、自动审批与高度自治。
- 模型训练、推理底层和提示词技巧大全。

## 5. 学习责任分配

用户优先亲手完成：

```text
测试场景和预期结果的设计
测试中关键 arrange / act / assert
部署拓扑的复述
根据症状提出第一轮故障假设
Agent 工具的能力、参数、返回和安全边界
一个真实只读工具的关键适配代码
每个闭环结束后的抽象总结
```

AI 可以优先承担：

```text
重复配置和脚手架
机械性的测试数据与清理代码
构建、编译和回归命令
环境状态采集
日志切片和候选故障范围整理
格式、文档、Git 范围检查与收尾
```

AI 自动完成机械工作时，仍要说明：

```text
它属于哪一层
输入和输出是什么
为什么需要
成功与失败分别看什么证据
```

## 6. 每轮统一学习节奏

每轮只保留一个根问题：

```text
先给当前黑盒和完整数据流
→ 用户做一个有依据的预测
→ 打开最多 5 个核心文件或组件
→ 只向下钻一个必要机制
→ 做一个最小实验
→ 读取运行证据
→ 回到总图修正模型
→ 决定是否值得记笔记
```

默认限制：

```text
一个解释簇只下钻一层
同时最多两个支线
每轮至少一个正常或失败证据
环境问题连续阻塞时，先修环境，不继续叠加新概念
部署和 Agent 不在同一天第一次展开
```

## 7. 按近期实际节奏安排的时间

### 估算依据

最近三个有效学习日形成的真实产出大致是：

```text
2026-07-23：
后端 CRUD 纵向切片 + 编译证据

2026-07-24：
状态规则、权限、前端页面、浏览器与 MySQL 证据

2026-07-25：
可空字段边界、7 个 Service 测试、笔记与 Git 收尾
```

这说明当前较稳定的学习吞吐是：

```text
每天 1 个完整证据簇
≈ 1～2 个核心机制
≈ 1 次实现、运行或故障验证
```

提交数量只能证明工程产出，不能直接等于理解程度。因此本计划按“有效学习日”而不是固定小时安排。

### 当前日历约束：空窗前、空窗期和返场

当前在约 3～4 个有效学习日后会出现一周左右的学习空窗。空窗前不追求完成整个 6A，而是先把四张总图建立牢：

#### 空窗前第 1 天：测试证据图

```text
Service 数据库测试
Controller / 权限测试
真实 HTTP 冒烟
```

目标：能说明三种证据分别覆盖和遗漏什么，并完成一个参数或权限测试证据。

#### 空窗前第 2 天：构建与运行图

```text
源码
→ Maven
→ JAR
→ 配置
→ Java 进程
→ 端口与日志
```

目标：知道 IDE 启动替我们隐藏了什么，并留下 JAR 或独立进程证据。

#### 空窗前第 3 天：部署与请求图

```text
浏览器
→ Nginx
→ Gateway
→ 业务服务
→ MySQL / Redis / Nacos
```

目标：认识容器、进程、端口、Volume 和 HTTP 跳转的责任边界；至少观察一个正常或失败运行证据。

#### 空窗前第 4 天（如时间允许）：Agent 双栈预览

```text
Spring AI Java 原生闭环
→ Python 旁路迁移闭环
→ 云模型 / Ollama 只是可替换提供方
```

目标：只建立架构和配置边界。环境顺利时可跑一次现有 Spring AI 工具；不在空窗前强行完成 Python Agent。

### 一周空窗期：每天 10～20 分钟轻复习

不要求打开完整开发环境，不写新功能。每天只做一张卡：

```text
第 1 天：凭记忆画三种测试及证据范围
第 2 天：写出源码到 JAR 再到进程
第 3 天：画容器、端口、Volume 和数据
第 4 天：画浏览器到 Nginx、Gateway、Service
第 5 天：用“现象 → 边界 → 证据 → 根因”复述排错
第 6 天：画模型、工具、Java Service 和数据库
第 7 天：不看笔记画完整第 6 步总图，留下三个仍模糊的问题
```

复习只追求重新唤醒线索，不要求背类名、注解和命令参数。

### 返场后的第一天：恢复而不是直接开新内容

```text
运行一个既有测试
→ 启动最小依赖
→ 发出一个真实请求
→ 对照总图定位每个证据
```

四个动作成功后再继续剩余 6A；不用从头重学。

### 推荐总量

```text
正常节奏：11 个有效学习日
状态很好：9 个有效学习日
环境故障较多：允许延长到 13 个有效学习日
```

相比 v0.1 多出的一个有效学习日用于 Python 跨语言迁移。空窗期的轻复习不计入有效实现日。不为了赶日期压缩抽象复盘，也不因为遇到一个底层函数就无限延长。

### 6A：建议 6 个有效学习日

#### 2026-07-27 上午检查点

上午先完成了进入测试前的权限机制复习，没有继续向 AOP、JVM 和 Spring Security 源码横向扩张。

第一遍先建立了角色图：

```text
@EnableMethodSecurity
→ 启动时把方法权限检查能力接入 Spring

方法权限拦截器
→ 每次在目标方法执行前读取规则并作出允许 / 拒绝决定

@PreAuthorize
→ 只保存这个方法自己的权限规则

@ss.hasPermission(...)
→ 调用 Yudao 提供的权限判断 Bean
```

后续复述证明根因不只是“少讲了代理”，而是把静态角色图误当成了伪代码：组件职责看似齐全，却没有一个能在脑中运行的具体事件。用户通过追问生命周期、匹配依据、第一接收者和包装范围，最终补齐为：

```text
@EnableMethodSecurity 启动装配
→ 注册“PreAuthorize.class 匹配规则 + 权限拦截器”
→ Spring 为命中的 Bean 创建代理
→ 方法调用先进入代理
→ 匹配器按 PreAuthorize.class 判断
→ 拦截器读取 value
→ 放行或拒绝原方法
```

本轮还形成了学习流程修正：角色图只负责导航，不能叫伪代码；机制问题必须选择一次真实事件，按“阶段 → 明确调用者 → 输入/状态 → 匹配依据 → 下一位接收者 → 结果分支/返回位置”动态模拟。框架自动行为再补齐“注册连接 → 运行时载体 → 匹配规则 → 执行器 → 分支”，但不自动深入代理源码。该规则已经进入 Architecture Learning Protocol v1.0。

下午不继续下钻代理、Advisor 和表达式解析源码，转入“不同测试分别能证明什么”。具体入口见：

- [第 6 步：下午测试学习工作台](第6步-下午测试学习工作台.md)

## 8. 动态调整规则

计划不是写死的。出现以下情况时这样调整：

```text
概念听懂但不能预测
→ 增加一个更小的真实实验，不增加新框架名

类和组件越来越多
→ 回到黑盒图，只保留所有者、输入、输出和责任

环境问题占满一轮
→ 将本轮改为排错轮，不同时学习新的 Agent 内容

测试代码能照抄但说不清证明范围
→ 暂停增加案例，先比较证据边界

Agent 能调用但业务边界模糊
→ 回到 Service / API 契约，不继续增加工具

连续两轮明显快于计划且能够独立复述
→ 合并下一轮，但保留运行证据和收尾
```

## 9. 第 6 步完成标准

### 6A 完成

用户能够解释并实际完成：

```text
测试证明
→ 构建产物
→ 运行配置
→ 依赖服务
→ 进程和端口
→ Nginx 与浏览器
→ 日志和故障定位
```

项目不再只能依赖 IDE 启动。

### 6B 完成

用户能够解释并实际完成：

```text
自然语言
→ 模型选择工具
→ 参数进入 Java
→ 复用已有业务能力
→ 返回结构化结果
→ 模型形成回答
```

并能说明只读限制、权限、数据范围、错误和审计边界。

### 总完成

面对另一个小型 Java 项目，用户能够先建立：

```text
怎样测试它
怎样构建和运行它
依赖和入口在哪里
失败时先看什么证据
哪些能力可以安全地暴露给 Agent
```

而不是只能复现本项目的命令和注解。
